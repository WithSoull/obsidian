# Литература — рейтинг чтения

Связано: [[Литература — ресерч]]

> Рабочий индекс литературы для ВКР. Здесь не дублируется полный backlog: задача этой заметки — определить, **что реально читать целиком, что достаточно просаммарить, что использовать только как точечную ссылку**, и отделить свежие источники для ВКР от старых фундаментальных работ «для себя».
>
> Дата актуализации: **2026-09-10**.

## Политика по свежести источников

Для основной библиографии ВКР приоритет такой:

- **2024–2026** — максимальный приоритет;
- **2022–2023** — основной рабочий диапазон;
- **2021** — граница пятилетнего окна, брать только сильные и непосредственно полезные работы;
- **2020 и старше** — не использовать для доказательства текущего состояния области, цен, характеристик современного железа или актуальности; оставлять только как фундаментальные / исторические источники либо когда работа является прямым предшественником нашей постановки;
- официальная документация AWS / Ceph и других продуктов может использоваться независимо от года исходной публикации страницы, но фиксируется **дата обращения: 2026-09-10**.

Рабочая цель для итогового списка литературы: сделать так, чтобы **большинство научных источников было 2022–2026 годов**, а старые работы были явно оправданы своей фундаментальностью.

Статусы:

- **READ** — прочитать статью полностью и сделать подробный паспорт;
- **SUMMARY** — получить качественное summary по полному тексту, затем вручную прочитать ключевые разделы;
- **CITE** — достаточно проверить тезис, библиографию и нужный фрагмент перед цитированием;
- **PERSONAL** — читать не ради формального списка ВКР, а для понимания storage / distributed systems.

# Главный рейтинг

## S — READ: прочитать полностью в первую очередь

### 1. Savva, Kakoulli, Herodotou — *Machine Learning-Based Caching and Tiering in Modern Data Storage Systems: A Survey*

- **Год:** 2026
- **Свежесть:** максимальная
- **Venue:** ACM Computing Surveys
- **Статус:** READ
- **Ссылка:** https://doi.org/10.1145/3803857
- **Почему:** главный современный обзор всей области ML-based caching / tiering. Должен дать карту терминов, моделей, признаков, datasets, baselines, metrics и bibliography.
- **Что выписать:** taxonomy задач; prediction targets; признаки; модели; baseline; системные метрики; open problems; какие работы авторы считают state of the art.

### 2. Motta et al. — *A multiclass cost–latency aware framework for multi-tiered cloud storage optimization via access pattern forecasting*

- **Год:** 2026
- **Свежесть:** максимальная
- **Venue:** Computer Communications
- **Статус:** READ
- **Ссылка:** https://www.sciencedirect.com/science/article/pii/S0140366426000277
- **Почему:** один из ближайших свежих аналогов: прогноз access pattern → решение о tier → cost / latency trade-off.
- **Что выписать:** target ML; признаки; horizon; cost model; классы хранения; ограничения; dataset; baselines; end-to-end metrics.

### 3. Mukherjee et al. — *Towards Optimizing Storage Costs on the Cloud (SCOPe)*

- **Год:** 2023
- **Свежесть:** основной диапазон
- **Venue:** IEEE ICDE
- **Статус:** READ
- **Ссылка:** https://research.adobe.com/publication/towards-optimizing-storage-costs-on-the-cloud/
- **Почему:** очень важна для нашей архитектуры **prediction → decision / optimization**. Прогноз сам по себе не выбирает tier — он является входом оптимизатора.
- **Что выписать:** математическую постановку; objective; prediction target; cost terms; planner; constraints; методику эксперимента.

### 4. Liu, Pan, Liu — *RLTiering: A Cost-Driven Auto-Tiering System for Two-Tier Cloud Storage Using Deep Reinforcement Learning*

- **Год:** 2023
- **Свежесть:** основной диапазон
- **Venue:** IEEE Transactions on Parallel and Distributed Systems
- **Статус:** READ
- **Почему:** сильный ближайший интеллектуальный аналог в двухуровневом storage. Нужен не для копирования RL, а чтобы понять максимально «тяжёлую» постановку auto-tiering и обосновать более простой/объяснимый подход.
- **Что выписать:** state/action/reward; migration cost; workload; baselines; преимущества и цена RL; какие проблемы возникают с объяснимостью и адаптацией.

### 5. Khan et al. — *Cloud storage tier optimization through storage object classification*

- **Год:** 2024
- **Свежесть:** высокая
- **Venue:** Computing
- **Статус:** READ
- **Ссылка:** https://link.springer.com/article/10.1007/s00607-024-01281-2
- **Почему:** прямо про storage objects и несколько tier; полезна для baseline и формулировки различий между classification и прогнозированием будущих обращений.
- **Что выписать:** признаки size/age/frequency; типы tier; rule-based подход; decision criteria; эксперимент.

### 6. Pang et al. — *Adaptive Intelligent Tiering for modern storage systems*

- **Год:** 2023
- **Свежесть:** основной диапазон
- **Venue:** Performance Evaluation
- **Статус:** READ
- **Ссылка:** https://www.sciencedirect.com/science/article/pii/S0166531623000020
- **Почему:** adaptive tiering и изменяющиеся access patterns — очень близко к тезису о динамической востребованности объектов.
- **Что выписать:** workload drift; признаки; кандидатура объектов на migration; метрики; механизм адаптации.

### 7. Chen et al. — *Workload-aware storage policies for cloud object storage*

- **Год:** 2022
- **Свежесть:** основной диапазон
- **Venue:** Journal of Parallel and Distributed Computing
- **Статус:** READ
- **Ссылка:** https://www.sciencedirect.com/science/article/abs/pii/S0743731522000326

### 8. Wong et al. — *Baleen: ML Admission & Prefetching for Flash Caches*

### 9. Татарникова Т. М., Архипцев Е. Д. — «Алгоритм контроллера нечеткой логики для размещения файлов в системе хранения данных»

# Старые, но слишком важные для диплома, чтобы выбрасывать

Эти работы выходят за предпочтительное окно 2022–2026. В тексте ВКР использовать **только там, где важна история подхода или это прямой предшественник**, и по возможности рядом ставить свежий источник.

### Herodotou, Kakoulli — *Automating Distributed Tiered Storage Management in Cluster Computing*

- **Год:** 2019
- **Статус:** READ, несмотря на возраст
- **Почему оставить:** один из прямых предшественников ML-based tiering. Без него легко ошибочно заявить, что прогнозирование обращений для tiering — новая идея.

### Ren et al. — *A machine learning assisted data placement mechanism for hybrid storage systems*

- **Год:** 2021
- **Статус:** SUMMARY
- **Почему оставить:** находится на границе пятилетнего окна; pipeline признаки + history → prediction → placement очень близок к нашей архитектуре.

### Советов Б. Я., Татарникова Т. М., Пойманова Е. Д. — «Организация многоуровневого хранения данных»

- **Год:** 2019
- **Дата публикации:** 2019-04-22
- **Venue:** Информационно-управляющие системы, № 2, с. 68–75
- **DOI:** 10.31799/1684-8853-2019-2-68-75
- **Статус:** SUMMARY / исторический related work
- **Почему оставить:** очень близкая русская работа: метаданные + частота обращения + сеть Кохонена для размещения в многоуровневой СХД. Для формальной «свежести» слабая, но для понимания отечественного related work крайне полезна.

- **Статус:** CITE / исторический related work
- **Почему оставить:** вертикальное/горизонтальное размещение, metadata, migration и Kohonen network.

### Татарникова Т. М., Пойманова Е. Д. — «Методика дифференцированного наращивания емкости системы хранения данных с многоуровневой структурой»

# PERSONAL — старые статьи, которые стоит прочитать для себя

> Они **не входят в основной freshness-пул ВКР**. Это отдельная полка: статьи, которые могут сильно улучшить понимание object/blob storage и распределённых систем. Дата здесь не недостаток — ценность в фундаментальных инженерных идеях.

## f4: Facebook's Warm BLOB Storage System

- **Год:** 2014
- **Venue:** USENIX OSDI
- **Статус:** PERSONAL / READ
- **Ссылка:** https://www.usenix.org/conference/osdi14/technical-sessions/presentation/muralidhar
- **Почему читать:** почти идеальная «статья для тебя» в контексте диплома. Facebook анализирует access patterns BLOB-объектов, выделяет hot/warm temperature zones и строит отдельную систему для менее востребованных BLOB. Тут storage economics, erasure coding/replication, failure domains и реальные production trade-offs.

## Pelican: A Building Block for Exascale Cold Data Storage

- **Год:** 2014
- **Venue:** USENIX OSDI
- **Статус:** PERSONAL / READ
- **Ссылка:** https://www.usenix.org/conference/osdi14/technical-sessions/presentation/balakrishnan
- **Почему читать:** показывает, что «cold storage» — это не просто медленный диск. Архитектура целиком проектируется вокруг другого workload profile и другого provisioning CPU/power/network/disk resources. Отлично вправляет мозги насчёт resource constraints.

## Finding a Needle in Haystack: Facebook's Photo Storage

- **Год:** 2010
- **Venue:** USENIX OSDI
- **Статус:** PERSONAL / READ
- **Ссылка:** https://www.usenix.org/conference/osdi10/finding-needle-haystack-facebooks-photo-storage
- **Почему читать:** классика хранения огромного количества immutable-ish BLOB/photo objects. Много полезного про metadata bottlenecks, filesystem overhead и design under real workload.

## Ceph: A Scalable, High-Performance Distributed File System

- **Год:** 2006
- **Venue:** USENIX OSDI
- **Статус:** PERSONAL / READ
- **Ссылка:** https://www.usenix.org/conference/osdi-06/ceph-scalable-high-performance-distributed-file-system
- **Почему читать:** фундамент Ceph/CRUSH. Особенно полезно для понимания разделения metadata/data paths, deterministic placement, heterogeneous unreliable devices и того, почему distributed storage не должен держать гигантскую централизованную таблицу размещения каждого блока.

## Dynamo: Amazon's Highly Available Key-value Store

- **Год:** 2007
- **Venue:** ACM SOSP
- **DOI:** 10.1145/1294261.1294281
- **Статус:** PERSONAL / READ
- **Почему читать:** consistent hashing, quorum, sloppy quorum, hinted handoff, vector clocks, anti-entropy, eventual consistency. Не S3-paper напрямую, но фундаментальная distributed-systems статья из Amazon; полезна намного шире диплома.

## Windows Azure Storage: A Highly Available Cloud Storage Service with Strong Consistency

- **Год:** 2011
- **Venue:** ACM SOSP
- **Статус:** PERSONAL / READ
- **Ссылка:** https://azure.microsoft.com/en-us/blog/sosp-paper-windows-azure-storage-a-highly-available-cloud-storage-service-with-strong-consistency/
- **Почему читать:** production cloud storage architecture: front-end / partition / stream layers, storage stamps, replication, scaling and strong consistency. Очень хороший системный аналог для размышлений о границах OpenS3-компонентов.

## The Tail at Scale

- **Год:** 2013
- **Venue:** Communications of the ACM
- **Статус:** PERSONAL / READ
- **Ссылка:** https://research.google/pubs/the-tail-at-scale/
- **Почему читать:** не про S3 напрямую, но одна из самых полезных коротких работ для backend/distributed systems. Объясняет, почему tail latency становится системной проблемой при fan-out и большом масштабе — пригодится и для storage, и для любой будущей bigtech-разработки.

# Практическое правило саммаризации

Для **READ**-статьи делать полный паспорт по шаблону из [[Литература — ресерч]] и отдельно фиксировать 3–7 тезисов, которые реально могут попасть в диплом.

Для **SUMMARY**-статьи сначала получать summary по полному тексту, после чего вручную читать минимум: abstract, introduction/related work, постановку задачи, evaluation, limitations/conclusion. Если статья становится опорной для нашей формулы, baseline или архитектуры — повышать её до READ.

Для **CITE**-источника не надо тратить час на полный текст: найти конкретный тезис, проверить первоисточник и записать точную страницу/раздел для будущей ссылки.

Для каждого источника при обработке обязательно записывать **год публикации** и **дату обращения к онлайн-версии**, если в библиографии будет URL. Для журналов ВАК/Белого списка перед финальной сдачей отдельно перепроверить статус площадки, поскольку перечни могут измениться.
