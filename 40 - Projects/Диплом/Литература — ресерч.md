# Литература — ресерч

> Черновой пул источников для ВКР по интеллектуальной СППР размещения объектов между классами S3-совместимого объектного хранилища.
>
> Цель заметки — собрать широкий набор работ для литературного обзора, введения, формальной постановки и экспериментальной части. Перед финальным включением в список литературы отдельно проверить библиографические данные, индексацию Scopus / Web of Science, квартиль и уровень в российском Белом списке на дату оформления ВКР.

## Критерии отбора

Приоритет источников:

1. Рецензируемые статьи и обзоры из сильных журналов и конференций по системам хранения, распределённым системам, cloud computing и ML.
2. Публикации, индексируемые Scopus / Web of Science; для российских требований дополнительно проверять Белый список и ВАК там, где это применимо.
3. Свежие работы 2023–2026 годов — для доказательства актуальности темы.
4. Более старые фундаментальные работы — для истории подходов, baseline-политик и формализации задачи.
5. Официальная документация производителей допустима как первичный источник для описания поведения конкретного продукта: AWS S3 Lifecycle / Intelligent-Tiering, Ceph device classes и т. п.

Обозначения приоритета:

- ★★★ — читать и саммарить в первую очередь;
- ★★ — полезный related work / источник для отдельных тезисов;
- ★ — вспомогательный или исторический источник.

## Рейтинг: что читать, что саммарить, что использовать точечно

Рейтинг построен не только по престижу публикации, а по полезности именно для этой ВКР. Цель — не прочитать пятьдесят работ от корки до корки, а глубоко понять ближайшие аналоги, корректно поставить эксперимент и иметь достаточный набор источников для каждого тезиса.

## Официальная документация как первичный источник

Научная статья не нужна там, где описывается конкретная семантика продукта. Для таких утверждений лучше ссылаться непосредственно на документацию производителя.

### AWS S3 Intelligent-Tiering

**Ссылка:** https://docs.aws.amazon.com/AmazonS3/latest/userguide/intelligent-tiering-overview.html

Использовать для:

- автоматического отслеживания access patterns;
- различий между Frequent / Infrequent / Archive Instant Access tiers;
- корректного разграничения Intelligent-Tiering и Lifecycle.

Важно: не писать, что любой COLD tier обязательно имеет часовую задержку. Это зависит от конкретного класса; автоматические уровни Intelligent-Tiering имеют другую семантику, чем архивные Glacier-классы.

### AWS S3 Lifecycle

**Ссылка:** https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-transition-general-considerations.html

Использовать для:

- transition actions;
- правил перехода между storage classes;
- ограничений и стоимости переходов;
- доказательства того, что Lifecycle и Intelligent-Tiering — разные механизмы.

### AWS S3 Storage Classes

**Ссылка:** https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html

Использовать для:

- назначения разных storage classes;
- сравнения latency / availability / retrieval semantics;
- минимальных сроков хранения и retrieval fees там, где они применимы.

### Ceph CRUSH device classes

**Ссылка:** https://docs.ceph.com/en/latest/rados/operations/crush-map/

Использовать для:

- реального примера self-hosted storage с разными классами физических устройств;
- аргумента, что storage infrastructure может различать `hdd`, `ssd`, `nvme` и строить placement rules по device class;
- поддержки on-prem постановки OpenS3, где денежная цена не обязана быть встроенным свойством класса.

## Как раскладывать источники по разделам ВКР

### Актуальность и предметная область

Основные кандидаты:

- Savva et al., 2026;
- Motta et al., 2026;
- Таст, Мосева, 2026;
- Татарникова, Пойманова, 2019 — модель многоуровневой СХД;
- ГОСТ Р 72413-2025;
- AWS S3 Storage Classes;
- AWS S3 Lifecycle;
- AWS S3 Intelligent-Tiering;
- Ceph CRUSH device classes.

Тезисы:

- существуют разнотипные storage tiers;
- объекты имеют различающиеся access patterns;
- размещение влияет на стоимость, ёмкость и latency;
- problem space остаётся активной областью исследований в 2026 году.

### Существующие методы решения

Разделить минимум на пять групп:

1. **Rule-based lifecycle policies** — AWS Lifecycle.
2. **Recency / frequency / online algorithms** — LRU, LFU, FIFO, Keep Hot or Go Cold, To Transfer or Not, SIEVE, Маличенко.

## Главный вывод для narrative ВКР

Нельзя строить литературный обзор вокруг тезиса:

> «Существующие системы используют простые правила, а мы впервые используем ML для tiering».

Это неверно. ML, deep learning, reinforcement learning, нейросети Кохонена и нечёткая логика для caching / tiering / data placement исследуются уже много лет; к 2026 году существует отдельный свежий зарубежный survey и несколько отечественных работ по интеллектуальному управлению многоуровневым хранением.

Более защищаемая позиция:

> Существующие подходы к управлению многоуровневым хранением варьируются от заранее заданных lifecycle-правил и online-эвристик до методов кластеризации, нечёткой логики, машинного обучения и reinforcement learning. Эффективность интеллектуального подхода зависит от характера нагрузки, используемой функции затрат и эксплуатационных ограничений. В работе предлагается отделить прогнозирование будущей востребованности объектов от принятия решения об их размещении и экспериментально оценить вклад прогноза относительно сильных эвристических политик в S3-совместимой self-hosted системе.

Отдельно для сравнения с российскими работами: наиболее близкие отечественные публикации используют сеть Кохонена или нечёткую логику для распределения файлов либо прогнозируют общий рост объёма хранения. В нашей постановке прогнозируется будущая востребованность отдельных объектов, а решение о размещении принимает отдельный planner с ёмкостными, производительными, миграционными и стоимостными ограничениями. Перед финальной формулировкой этого отличия проверить детали выбранных российских статей после полного чтения.

### IBM Cloud Object Storage traces

Источник: Eytan et al., *It's Time to Revisit LRU vs. FIFO*, HotStorage 2020.

Что известно из текущего ресерча:

## Исследовательская позиция после ресерча

Работа должна проверять не тезис «ML лучше», а условия его применимости.

Рабочая гипотеза:

> Для нагрузок с устойчивой предсказуемой структурой обращений использование ML-прогноза востребованности в общем планировщике может улучшить системный результат по сравнению с настроенными эвристическими политиками при одинаковых ограничениях.

Нулевая гипотеза:

> Практически значимое улучшение относительно лучшего эвристического baseline отсутствует.

На хаотичной нагрузке преимущество ML может исчезать — это нормальный и полезный отрицательный результат, а не провал эксперимента.
