## История сетевых API
- Веб-сервисы — продолжение старых технологий взаимодействия по сети.
- EJB и RMI — ограничены Java.
- DCOM — ограничен платформами Microsoft.
- CORBA — чрезмерно сложен и несовместим.
- Все основаны на RPC (Remote Procedure Call).
## Идея RPC
- Делает удалённый вызов похожим на локальный.
- Абстракция называется *location transparency*.
- Проблема: сетевые вызовы принципиально отличаются от локальных.
## Основные недостатки RPC
1. Сеть непредсказуема, возможны потери и задержки. А RPC пытается скрыть это.
2. Возможны таймауты без информации о результате.
3. Повторные запросы без идемпотентности вызывают дублирование.
4. Сетевые задержки варьируются, в отличие от локальных вызовов.
5. Параметры нужно сериализовать, что сложно для сложных структур.
6. Разные языки требуют преобразования типов данных.
## Современные RPC-фреймворки

- RPC остаётся актуальным, развивается на новых технологиях.
- Thrift, Avro поддерживают RPC.
- gRPC использует Protocol Buffers, поддерживает стриминг.
- Finagle — основан на Thrift, Rest.li — JSON/HTTP.
- Асинхронность реализуется через futures для упрощения ошибок и параллельных запросов.
- Обнаружение сервисов помогает клиенту найти IP и порт нужного сервиса.
## RPC vs REST
- RPC с бинарной кодировкой эффективнее JSON/REST по производительности.
- REST удобнее для публичных API — легко тестировать и отлаживать, поддерживается большинством языков и софтовой экосистемой.
- REST доминирует в публичных API, а RPC — во внутренних запросах организаций.
