### Разные схемы для *writer* и *reader*
На самом деле от этих схем требуется лишь быть совместимыми, не обязательно быть одинаковыми.

![[99 - Meta/02 - Медиа/Pasted image 20251104152035.png]]

Тут уже можно заметить:
1) Необязательно размещать поля в одинаковом порядке
2) Если поле есть в write scheme, но нет в reader scheme, то такое поле просо проигнорируется, в обратную сторону тоже самое, только уже нужно дефолтное значение какое-то. В reader scheme есть userID, которому должно присвоится дефолтное значение, если в write scheme, не будет этого поля.
### Scheme evolution rules
1) **Forward compability**
	- Новая write scheme
	- Старая read scheme
2) **Backward compability**
	- Старая write scheme
	- Новая read scheme
###### Добавление/Удаление полей
Чтобы поддерживать совместимость, можно добавлять/удалять только те поля, у которых есть дефолтное значение. 
Если вы добавите новое поле, у которого не будет дефолтного значения, новый reader не сможет прочитать данные написанные старым writer, таким образом ломается *backward compability*.
Если удалить обязательное поле, у которого нет дефолтного значения, то таким образом старые reader, не смогут ничего записать в это удаленное поле, и сломается уже *forward compability*.
###### Остальное
- Тип поля можно изменить, если Avro способен выполнить преобразование.  
- Имя поля также можно изменить, добавив псевдоним (alias) в схему чтения, чтобы распознать старое имя.  
- Переименование поля обеспечивает обратную совместимость, но не прямую.  
- Добавление новой ветви в union тип также сохраняет обратную совместимость, но нарушает прямую.

### Главный вопрос: Как на принимающей стороне узнают, какую версию/какую схему *writer* использовали для записи?
Неплохой вещью является базка соответсвий версий writer'ов и reader'ов. Это дает возможность сверить совместимость схем.
А теперь к способам решения нашей проблемы: оно безусловно зависит от контекста задачи. Под разные виды нагрузок будут хорошо подходить разные решения. Вот примеры некоторых из них:
###### 1. Large file with lots of records (*batch*)
Тут проще всего отправить 1 схему writer'а для всех этих записей. Стандартное использование Avro для Hadoop - милион записей, которые сделал один и тот же writer. У Avro даже есть специальный формат для такого файла (из многих записей) - *object container files*.
###### 2. Database with individually written records
Вот в базку например записи могут идти записи совершенно с разными схемами writer'a. Тут нормальным вариантом будет добавить несколько бит(байт) под код нужного writer'а. На стороне базки держать карту соотвествия: ключ -> writer's schema.
###### 3. Sending records over a network connections
Еще один интересный вариант, когда устанавливается соединение, внутри которого может будут отправляться данные записанные одним и тем же writer'ом: отправить его схему во время установки этого самого соединения. Так кстати и работает Avro RPC protocol.
