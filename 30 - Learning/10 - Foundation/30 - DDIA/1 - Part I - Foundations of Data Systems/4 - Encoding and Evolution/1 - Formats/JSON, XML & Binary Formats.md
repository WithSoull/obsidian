Есть стандартизированные форматы данных которые могут читать разные программы, JSON и XML являются основными конкурентами.
1) XML - критикуется за излишнюю массивность так скажем
2) JSON - имеет встроенную поддержку в браузере, поэтому так популярен
3) CSV - еще один популярный формат, но менее мощный

### Проблемы
Конечно, везде есть свои trade-of'ы, и эти ребята не исключения, у них есть минусы
###### 1. Слабая поддержка чисел
1) XML и CSV вообще не различают строки и числа, поэтому формально все есть строки
2) JSON различает строки и числа, но не различает числа целые и числа с плафающей запятой. Ну и нет соответсвенно инструментария, для обработки "точности" чисел с плавающей запятой.
С флотами все достаточно трудно. Взять числа большие чем `2^53` не могут быть представлены в IEEE 754 как число с плафающей запятой с двойной точностью (double / float64). Поэтому ребятам из твиттера приходится отправлять ID твитов дваждый, как число и как строку в JSON, чтобы избежать ошибок при десерлиализации данных.
###### 2. Поддержка *особых* символов
У XML/JSON хорошая поддержка Unicode, но нет поддержки бинарных строк. Так фича с бинарными строками весьма полезная, человечество придумала Base64, в котором есть поддержка бинарных строк, **НО** она чет херово работает, и увеличивает размер данных аж на 33%.
###### 3. Схема данных
В JSON/XML есть опциональная поддержка схемы. В XML использование схем распрастранено, а вот в случае с JSON эту схему не используют, что добавляет дополнительный оверхед на на бизнес логику. А CSV вообще не имеет схемы, и приложению нужно самому определить че там по строкам и стоблцам записано, а еще есть некие проблемы с экранированием разделителей, и некоторый парсеры плохо с этим работают. 
### Не все потеряно 
Не смотря на все эти проблемы, описанные выше, JSON, XML, CSV хороши для многих целей, иначе бы они не обрели бы такую популярность. А в ситуациях когда,  колобарации не могут договориться о форматах, скорее всего проблема именно в том, что компаниям надо согласовать все мелочи. Бюрократия.

## Бинарные форматы
Хорошо подходят для данных, которые летают внутри компании. Для маленького датасета выигрыш небольшой, но для терабайтов данных огромный импакт. JSON не такой многословный как XML, тем не менее, оба проигрывают в этом плане своим бинарным аналогам:
1) Для *JSON*:
   - MessagePack
   - BSON
   - BJSON
   - UBJSON
   - BISON
   - Smile
2) Для *XML*:
   - WBXML
   - Fast Infoset

Некоторые из них расширяют типы возможности с типами данных, например умеют различать целые числа от чисел с плавающей запятой, добавляют бинарные строки. Но тем не менее они не меняют структуру JSON/XML. На самом деле они просто представляют ту же информацию, но в бинарном виде. Им нужно включать в себя наименования полей даже.

Глянем на вот такой JSON:
``` json
{
	"userName": "Martin",
	"favoriteNumber": 1337,
	"interests": [
		"daydreaming",
		"hacking"
	]
}
```
