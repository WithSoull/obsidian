>[!quote] The limits of my language mean the limits of my world.

Выбор модели данных играет очень важную роль в разработке: не только как мы пишем ПО, но еще и как мы размышляем о проблемах, которые мы решаем.

Большинство приложений построены в несколько слоев моделей данных, одна модель поверх другой. Для каждого слоя мы мы задаемся вопросом: **Как нам представить текущий слой в терминах следующего(нижнего) слоя?**

>[!example] Пример
>1. Мы представляем **реальный мир** и моделируем в нем объекты, структуры и API, которая пользуется этими моделями.
>2. Когда мы хотим **хранить эти данные**, мы _выражаем_ их в терминах каких-то общих структур, вроде JSON и  XML.
>3. Инженеры, которые строят ПО баз данных решают каким образом разместить *JSON/XML/relational/graph* данные в терминах **битах в памяти, диске или сети**. Это позволяет нам запрашивать данные, искать их и манипулировать разными способами.
>4. И наконец _hardware engineers_ решают как представить эти самые битики в терминах **электрических микросхем, магнитных полей и тд**.

В больших приложениях есть промежуточные слои, API на API. 

>[!important] Ключевая идея
>Каждый слой должен прятать всю сложность и все тонкости нижнего слоя и предоставлять чистую модель данных

Такие абстракции позволяют людям работать вместе, параллельно, на разных слоях.
Существует очень много моделей данных, нужно выбирать подходящую с умом.

## NoSQL
>[!info] NoSQL - *Not Only SQL*

Причины появления NoSQL:
- Масштабируемость (большие данные, высокая скорость записи)
- Open Source предпочтительнее дорогих коммерческих СУБД
- Специализированные запросы (поиск, графы, JSON и т.д.)
- Гибкая схема данных, без жёстких ограничений SQL

### Какие бывают NoSQL модели?
- [[30 - Learning/10 - Foundation/30 - DDIA/1 - Part I - Foundations of Data Systems/2 - Data Models and Query Languages/01 - Data Models/02 - Document/Document model|Document model]] - хорошо подходят для *One-To-One*, и несложных *Many-To-One* отношений c большими компромиссами. Некоторые СУБД поддерживают [[30 - Learning/10 - Foundation/30 - DDIA/1 - Part I - Foundations of Data Systems/2 - Data Models and Query Languages/01 - Data Models/02 - Document/MapReduce|MapReduce]].
- [[30 - Learning/10 - Foundation/30 - DDIA/1 - Part I - Foundations of Data Systems/2 - Data Models and Query Languages/01 - Data Models/03 - Graph/Graph model|Graph model]] - очень хорошо подходит для сложных *Many-To-Many* отношений.
- Key-Value - всем известный redis и memcache
- Wide-Column - которые хорошо подходят под OLAP нагрузку

## Hierarchical model - IMS (1968, IBM)
- Самая популярная СУБД 1970-х (для бизнеса, изначально для Apollo).
- Использовала иерархическую модель (данные как дерево записей, похоже на JSON).
- Хорошо подходит для one-to-many.
- Плохо работает с *Many-To-Many* и JOIN-ами.
- Выбор для разработчика:
  - дублировать данные (денормализация),
  - или вручную разрешать ссылки.

Проблемы тех лет аналогичны проблемам документных БД сегодня.
#### Ответы на ограничения
- **Реляционная модель** → SQL → стала доминирующей.
- **Сетевая модель** → имела популярность, но со временем исчезла.
- В 1970-х шла «великая дискуссия» между двумя лагерями.
---
## Network model (CODASYL)
- Стандартизирована комитетом CODASYL, реализована разными вендорами.
- Обобщение иерархической модели:
  - В иерархической: у записи только 1 родитель. - В сетевой: запись может иметь несколько родителей.
  - Пример: "Greater Seattle Area" = 1 запись, к ней ссылаются все пользователи из региона.
  - Позволяет моделировать many-to-one и many-to-many.
#### Особенности
- Связи = не foreign keys, а ссылки/указатели (на **диске**).
- Доступ к данным только по **access path**.
- Запрос = перемещение курсора по связям (итерация списков, переход по указателям).
- Программист должен сам отслеживать возможные пути к одной записи. Когда связи many-to-many часто можно дойти до точки назначения несколькими способами. И это надо держать в уме.
#### Проблемы
- Запросы = ручная навигация по структуре (как linked list или n-мерное пространство).
- Из-за этого код становился сложным и негибким.
- Если доступного пути к данным нет → трудно достать нужное.
- Изменение access path → необходимость переписывать весь код работы с БД.
- Трудно менять модель данных приложения.
### Плюсы (для 1970-х)
- Максимально эффективно использовала слабое железо (ленточные накопители, медленные [[30 - Learning/10 - Foundation/30 - DDIA/1 - Part I - Foundations of Data Systems/2 - Data Models and Query Languages/03 - Concepts and Performance/Disk Seek vs Disk Bandwidth|disk seek]]).

## Document DB VS Relational DB

| Характеристика                                                                                                      | Document DB                                                                                                                                     | Relational DB                                                                                                                                              |
| ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Схема данных**                                                                                                    | [[Schema On-Read vs On-Write|Schema-On-Read]] (гибкая, без жёсткой схемы) | [[Schema On-Read vs On-Write|Schema-On-Write]] (строгая схема, валидация при записи) |
| **Структура данных**                                                                                                | Древовидная, иерархическая (one-to-many встроенные)                                                                                             | Табличная, нормализованная                                                                                                                                 |
| **Вложенность**                                                                                                     | Нативная поддержка вложенных объектов и массивов                                                                                                | Требует разбиения на таблицы (shredding)                                                                                                                   |
| **One-to-many связи**                                                                                               | Хранятся внутри родительского документа                                                                                                         | Отдельные таблицы с foreign key                                                                                                                            |
| **Many-to-one связи**                                                                                               | **Document reference**, требует *дополнительных* запросов                                                                                       | **Foreign key + JOIN** (*эффективно*)                                                                                                                      |
| **Many-to-many связи**                                                                                              | Document reference, множественные запросы (*неудобно*)                                                                                          | Связующая таблица + JOIN (*удобно*)                                                                                                                        |
| **JOIN операции**                                                                                                   | Плохая поддержка, эмуляция через несколько запросов                                                                                             | Нативная поддержка, оптимизированы                                                                                                                         |
| **[[Data Locality|Локальность данных]]** | *Высокая* (весь документ загружается целиком)                                                                                                   | *Низкая* (данные разнесены по таблицам)                                                                                                                    |
| **Производительность чтения**                                                                                       | *Быстрая* для полной загрузки документа                                                                                                         | *Медленнее* при необходимости JOIN'ов                                                                                                                      |
| **Денормализация**                                                                                                  | Часто требуется для производительности                                                                                                          | Обычно избегается                                                                                                                                          |
| **Консистентность при денормализации**                                                                              | Ручная поддержка, больше работы                                                                                                                 | Меньше проблем благодаря нормализации                                                                                                                      |
| **Прямые ссылки на вложенные элементы**                                                                             | Нет (пока структура неглубокая — не проблема)                                                                                                   | Прямой доступ через индексы и ключи                                                                                                                        |
| **Близость к структурам приложения**                                                                                | Высокая (JSON/BSON близки к объектам ОО языков)                                                                                                 | Требует маппинга (ORM)                                                                                                                                     |
| **Access path**                                                                                                     | Гибкие, не жёсткие (в отличие от CODASYL)                                                                                                       | Определяются индексами и ключами                                                                                                                           |
## Which data model leads to simpler application code? 

>[!quote] For **highly interconnected** data, the **document model is awkward**, the **relational model is acceptable**, and **graph models are the most natural**.
###### Document DB предпочтительнее когда:
- Данные имеют древовидную структуру (one-to-many)
- Документ загружается и сохраняется целиком
- Мало связей many-to-one и many-to-many
- Нужна гибкость схемы (evolving schema)
- Важна [[30 - Learning/10 - Foundation/30 - DDIA/1 - Part I - Foundations of Data Systems/2 - Data Models and Query Languages/03 - Concepts and Performance/Data Locality|локальность данных]] для производительности
###### Relational DB предпочтительнее когда:
- Множество связей many-to-one и many-to-many
- Часто требуются JOIN операции
- Нужна строгая схема и валидация
- Важна нормализация и устранение дублирования
- Требуется атомарный доступ к фрагментам данных

# Разные языки запросов
Когда реляционные модельки только появились они принесли с собой новый способ обработки запросов: SQL - *декларативный язык*, в то время как IMS и CODASYL использовали императивный язык. Что это значит?
##### *Declarative* language VS *Imperative* language
``` js
// Так выглядит императивный язык
function getSharks() {
  var sharks = [];
  for (var i = 0; i < animals.length; i++) {
    if (animals[i].family === "Sharks") {
      sharks.push(animals[i]);
    }
  }
  return sharks;
}

```

``` sql
# а так декларативный
select * from animals where family = 'Sharks';
```

Императивный язык говорит в каком порядке, что делать, код испольняется строчкой за строчкой. А SQL в свою очередь: мы указываем паттерн данных, которые хотим получить. В декларативном языке скрыта вся реализация. Так же декларативный язык лучше подходит для параллельного выполнения. К слову HTML тоже декларативный.
