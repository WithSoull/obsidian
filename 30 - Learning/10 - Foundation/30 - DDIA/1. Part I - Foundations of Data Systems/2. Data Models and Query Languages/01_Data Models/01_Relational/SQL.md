## Структура
- Таблица = коллекция строк (кортежей), без вложенных структур и путей доступа.
- Можно:
  - читать любые строки по условию,
  - находить строку по ключу,
  - вставлять новую строку без заботы о связях.

## История
Самая популярная модель данных на сегодня это SQL, которая основана на реляционной модели, предложенная **Эдгаром Кодом в 1970**: данные организованы в отношениях(relation), которые мы называем таблицами в SQL, каждое отношение(relation) это неупорядоченный набор кортежей (rows в SQL).

**Relational database management systems (RDBMSes)** и **SQL** был выбором многих на протяжении 25-30 лет - целая вечность для IT.

>[!quote] The **goal** of the relational model was to **hide that implementation detail** behind a cleaner interface.

## Object-Relational Mismatch

^5446c6

У **SQL** есть серьезная проблема, но ее вполне можно уже считать решенной
###### Impedance mismatch
- Программы пишутся на ООП-языках (объекты)
- SQL хранит данные в таблицах (строки/столбцы)
- Нужен "переводчик" между объектами и таблицами (ORM и т.п.)
- Несоответствие моделей = **impedance mismatch**
###### SQL (до 1999)
- Нормализованные таблицы: user, positions, education, contacts
- Связь через foreign keys
- Чтобы собрать профиль → JOIN или несколько запросов

###### Современный SQL (после 1999)
- Поддержка сложных типов: XML, JSON
- Можно хранить вложенные данные в строке
- Частичная поддержка индексов и запросов внутри JSON/XML

###### JSON как текст
- JSON хранится в колонке TEXT
- БД не умеет выполнять запросы внутри JSON
- Логику парсинга берёт на себя приложение

## Many-to-One and Many-to-Many Relationships
Это еще один нюанс с котороым можно столкнуться при использовании *relational* модели данных.

![[99 - Meta/02 - Медиа/Снимок экрана 2025-09-02 в 13.06.15.png]]

###### Как хранить информацию о регионе или компаниях? Через строку напрямую или в отдельной таблице? 
Какие плюсы хранения в одтельной таблице:
- Консистентный стиль и отсутствие ошибок
- Нет неоднозначности (например, одинаковые названия городов)
- Легко обновлять (переименование региона → правим 1 запись)
- Поддержка локализации (отображение на разных языках)
- Улучшенный поиск (иерархии: город → штат → страна)
- Отсутствие дублирования: название региона будет хранится лишь в одном месте, а в таблице `users` будем хранить `region_id`.  Иначе если потребуется обновить поле `region`, то придется делать это во всех местах, а это у нас **write overhead** и **risk inconsistencies**(обновили только часть данных). Удаление таких репликаций это идея **нормализации** в базах данных.
Поэтому мы создаем еще одну таблицу `regions` в которой будет условно `region_id` и `region_name`.

## В сравнении с другими моделями
#### Доступ к данным
- В сетевых/иерархических БД: программист сам задаёт **access path**.
- В реляционной БД: выбор пути делает **query optimizer** автоматически.
- Новые индексы подключаются прозрачно → запросы начинают их использовать без изменения кода.
#### Эффект
- Легче добавлять новые фичи в приложение.
- Оптимизатор сложный, но создаётся один раз → все приложения получают выгоду.
- В краткосрочной перспективе ручной выбор путей проще, но в долгосрочной выигрывает общий оптимизатор.

➡ Ключевая идея: автоматический выбор access path = гибкость и эволюция приложения без переписывания запросов.
