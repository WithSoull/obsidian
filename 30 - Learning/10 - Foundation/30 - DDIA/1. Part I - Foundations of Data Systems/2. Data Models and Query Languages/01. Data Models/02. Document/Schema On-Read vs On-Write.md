В случае document модели у нас есть схема на запись **schema-on-read**, в традиционых relational базах у нас **schema-on-write**. 
Тут похожий спор, как с динамической и статической типизацией. Обязательство делать схему это спортный вопрос, в котором нет правильного ответа.
Разница между подходами особенно заметна когда в ситуациях когда нужно поменять формат данных. Например, вы хранили полное имя пользователя в одном поле, и затем решили разбить фио по 2-ум полям.
В document модели проблема со старым форматом решается на уровне приложения вот так:
``` c++
if (user && user.name && !user.first_name) {
// Documents written before Dec 8, 2013 don't have first_name
	user.first_name = user.name.split(" ")[0];
}
```

Для schema-on-write это будет выглядить вот так на урове SQL миграции:
``` sql
ALTER TABLE users ADD COLUMN first_name text;
UPDATE users SET first_name = split_part(name, ' ', 1); -- PostgreSQL
UPDATE users SET first_name = substring_index(name, ' ', 1); -- MySQL
```

Здесь еще хочется подчеркнуть что изменение схемы считается долгой операцией, но это не совсем так, боьшинство реляционных бд делают `alter table` в считанные миллисекунды. Правда MySQL является одним из исключений так, как копируюется вся таблица целиком, это может вызывать простои вплоть до часов реального времени.

При этом, можно как в для документных моделек обновлять поле каждое чтение, перед этим создать поле first_name и по дефолту сделать его null.

Когда пользовтася schema-on-read:
1) У нас много разных типов данных
2) Структура данных определяется от каких-то внешних источников, предугадать которые мы попросту не можем.
