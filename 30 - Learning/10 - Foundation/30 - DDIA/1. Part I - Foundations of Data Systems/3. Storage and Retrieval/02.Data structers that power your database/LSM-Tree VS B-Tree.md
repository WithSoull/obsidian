Полагаться на одни бэнчмарки глупо, нужно подбирать структуру индекса отдельно под свой тип нагрузки.

>[!danger] Когда приложение очень часто записывает данные (например, логгирование, метрики, транзакции), то основное ограничение — это **возможности физического носителя** (HDD или SSD). Диск может выполнять лишь определённое количество мегабайт записей в секунду
>
>Чем больше write-amplification тем меньше удасться записать в реальности.


| Критерий                                 | B-Trees                                                                                                                                           | LSM-Trees                                                                                                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Архитектура**                          | Структура на основе фиксированных страниц (страница ~4KB), каждая страница содержит диапазон ключей. Изменения выполняются _in-place_ (на месте). | Лог-ориентированная структура. Новые данные всегда добавляются последовательно в новые файлы (SSTables), старые версии позже удаляются при компакции. |
| **Основной алгоритм записи**             | При вставке или обновлении значение записывается в страницу дерева. Если страница переполнена — происходит её split.                              | При записи данные добавляются в память (memtable), затем периодически сбрасываются на диск в виде SSTable. Периодически объединяются (compaction).    |
| **Write-Ahead Log (WAL)**                | Обязательно используется — каждая операция логируется дважды: в WAL и в саму страницу B-дерева.                                                   | WAL используется для надёжности до сброса memtable, но сама структура на диске — append-only.                                                         |
| **Write amplification**                  | Высокое — из-за многократных перезаписей страниц и WAL. Может достигать больших значений на SSD.                                                  | Ниже, поскольку большинство операций — последовательные записи. Однако компакция тоже повышает write amplification.                                   |
| **Производительность записи**            | Ограничена скоростью случайных записей (особенно на HDD).                                                                                         | Высокая — за счёт последовательной записи и группирования операций.                                                                                   |
| **Производительность чтения**            | Высокая для прямого доступа к ключам, т.к. структура всегда "актуальна" и ключ хранится в одном месте.                                            | Зависит от числа сегментов. Может требовать чтение из нескольких SSTables, если компакция не успевает.                                                |
| **Проблемы конкуренции при записи**      | Требует блокировок (latches) для синхронизации доступа к страницам.                                                                               | Минимальны — так как новые данные добавляются в новые сегменты, а старые заменяются атомарно.                                                         |
| **Фрагментация**                         | Присутствует — при split страниц некоторые остаются частично пустыми. Неэффективное использование диска.                                          | Низкая — периодическая компакция удаляет "мусор" и компактно упаковывает ключи.                                                                       |
| **Использование дискового пространства** | Есть потери из-за неиспользуемого места в страницах (особенно после splits).                                                                      | Более эффективно — данные постоянно перепаковываются при компакции, особенно при leveled compaction.                                                  |
| **Тип выполняемых операций диска**       | Случайные чтения/записи, требующие seek (особенно на HDD).                                                                                        | Последовательная запись больших файлов (SSTables). Выигрывает на HDD и на SSD с ограничением на случайные записи.                                     |
| **Последовательная/случайная запись**    | Случайная (каждая страница может быть в произвольном месте).                                                                                      | Последовательная (append-only логика).                                                                                                                |
| **Стабильность и предсказуемость**       | Очень стабильное время отклика (latency). Более предсказуемое поведение.                                                                          | Возможны пиковые задержки (spikes) при компакциях и фоновом слиянии файлов.                                                                           |
| **Поведение на SSD**                     | Write amplification сильно влияет на износ.                                                                                                       | Лучше адаптированы к SSD (внутренне SSD тоже используют лог-структуру).                                                                               |
| **Сопротивляемость износу**              | Плохо работают при большом количестве перезаписей на SSD.                                                                                         | Лучше, но зависят от настройки глубины и частоты компакции.                                                                                           |
| **Транзакционная изоляция / блокировки** | Простая реализация – ключ существует в одном месте, можно блокировать диапазоны. Хорошо подходит для ACID транзакций.                             | Сложнее, т.к. одна и та же запись может существовать в нескольких SSTables. Требуется дополнительная логика для изоляции транзакций.                  |
| **Сложность реализации**                 | Простая, проверенная временем, хорошо поддерживается в реляционных СУБД.                                                                          | Более сложна из-за фона компакций, merge-процессов и управления уровнями SSTables.                                                                    |
| **Типичные движки**                      | InnoDB (MySQL), PostgreSQL, SQLite, Oracle DB.                                                                                                    | LevelDB, RocksDB, Cassandra, HBase, ScyllaDB.                                                                                                         |
