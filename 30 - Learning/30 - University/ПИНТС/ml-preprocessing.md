# Предобработка данных в ML — объяснение для бэкендера

> **Контекст:** все техники применены в ПР4 ПИНТС перед обучением регрессионных моделей. Без правильной предобработки линейные модели дали бы некорректные результаты.

---

## Зачем вообще предобрабатывать данные

ML-модели — это математика. Математика работает неправильно, если:
- Числа в разных признаках несопоставимы по масштабу (distance_km: 0–50, пассажиры: 1–6)
- Целевая переменная имеет аномальное распределение (99% значений < 1000, один выброс = 100000)
- Признаки содержат категории (Y/N вместо 1/0)
- Данные содержат NaN или физически невозможные значения

Предобработка — это "нормализация входных данных" для модели, как нормализация JSON перед отправкой в API.

## 1. Масштабирование признаков (StandardScaler)

### Проблема

```python
# Данные без масштабирования:
distance_km:      0.5, 2.3, 15.7, 0.8   # диапазон: 0–50
pickup_latitude:  40.71, 40.75, 40.68   # диапазон: 40–41
passenger_count:  1, 2, 1, 4            # диапазон: 1–6
```

Для линейных моделей (Linear, Lasso, Ridge) признак `pickup_latitude` со значением 40.71 выглядит как "огромный" по сравнению с `passenger_count` = 1. Модель будет назначать веса исходя из масштаба, а не из реальной важности.

Для алгоритмов на расстояниях (KNN, SVM) маленький признак в диапазоне [0,1] будет "невидим" на фоне признака в диапазоне [40,41].

### Решение: StandardScaler

```python
from sklearn.preprocessing import StandardScaler

scaler = StandardScaler()
X_scaled = scaler.fit_transform(X)
```

Формула:
```
x_scaled = (x - mean) / std
```

**Что происходит:**
```python
# До масштабирования:
distance_km:     [0.5, 2.3, 15.7, 0.8]
# mean=4.825, std=6.5

# После:
distance_km:     [-0.66, -0.38, 1.67, -0.62]
# Теперь: mean=0, std=1
```

**После StandardScaler каждый признак:** среднее = 0, стандартное отклонение = 1. Все признаки на одном масштабе — модель сравнивает яблоки с яблоками.

### Когда масштабирование нужно, а когда нет

| Модель | Нужно масштабирование? |
|--------|------------------------|
| Linear Regression | **Да, обязательно** |
| Lasso | **Да, обязательно** (иначе alpha не работает правильно) |
| Ridge | **Да, обязательно** |
| Logistic Regression | **Да, обязательно** |
| KNN | **Да, обязательно** (работает на расстояниях) |
| Random Forest | Нет (деревья делают пороговые сравнения) |
| Gradient Boosting | Нет (та же причина) |
| Neural Networks | **Да, обязательно** |

### Важно: fit только на обучающих данных!

```python
# ПРАВИЛЬНО:
scaler.fit(X_train)           # считаем mean/std только на train
X_train_scaled = scaler.transform(X_train)
X_test_scaled  = scaler.transform(X_test)  # используем ту же статистику

# НЕПРАВИЛЬНО (data leakage!):
X_scaled = scaler.fit_transform(X)  # нельзя перед split
X_train, X_test = train_test_split(X_scaled)
# Почему плохо: тест-выборка "видела" обучающие данные через статистику scaler
```

## 2. Log-трансформация целевой переменной

### Проблема: скошенное распределение

Длительность поездки на такси имеет сильно скошенное вправо распределение:

```
Количество поездок:
│
5000 │█
4000 │███
3000 │█████
2000 │████████
1000 │██████████████
 500 │██████████████████
   0 │───────────────────────────→
      0  500 1000 2000 5000 10000  (секунды)
```

99% поездок — 100–3000 секунд. Но есть выбросы до 7000+ секунд. Это создаёт проблемы:

1. **Для модели:** она "видит" только малую долю пространства признаков
2. **Для метрик:** выброс в 7000 с создаёт огромную MSE и "отвлекает" модель
3. **Для предположений линейности:** линейная связь нарушается

### Решение: log1p-трансформация

```python
y = np.log1p(df['trip_duration'])
```

`log1p(x)` = `log(x + 1)` — добавляем 1, чтобы не было проблем при x=0.

**Что происходит с распределением:**

```
До (секунды):
│
│     ██
│   ████
│ ██████████
│─────────────→  скошено вправо

После log1p:
│
│     ████
│   ████████
│   ████████████
│ ██████████████████
│─────────────→  почти нормальное!
```

Нормальное распределение — это именно то, что предполагает линейная регрессия. После трансформации модель работает в "удобном" пространстве.

### Обратная трансформация для метрик

Модель обучена на `log1p(y)` и предсказывает `log1p(ŷ)`. Для интерпретации нужно вернуться:

```python
y_pred_log = model.predict(X_test)         # предсказание в log-масштабе
y_pred_sec = np.expm1(y_pred_log)          # обратная трансформация

# expm1(x) = e^x - 1 = точная обратная к log1p(x)

rmse = np.sqrt(mean_squared_error(y_test_sec, y_pred_sec))  # в секундах
```

**Почему R² считаем в log-масштабе:**

```python
r2 = r2_score(y_test, y_pred_log)  # на log-шкале, не на секундах
```

Это корректнее, потому что модель оптимизировалась в log-пространстве. R² в секундах был бы другим числом и менее информативным.

## 3. Кодирование категориальных признаков

### Проблема

ML-модели работают с числами. Как передать строку `'Y'` или `'N'`?

### Binary Encoding (для бинарных признаков)

```python
# store_and_fwd_flag: 'Y' или 'N'
df['store_and_fwd_flag'] = (df['store_and_fwd_flag'] == 'Y').astype(int)
# 'Y' → 1, 'N' → 0
```

### One-Hot Encoding (для многозначных категорий)

```python
# vendor_id: 1 или 2
# В нашем случае это числа, но концептуально:
pd.get_dummies(df, columns=['vendor_id'])
# vendor_id_1: 1, 0, 0, 1, ...
# vendor_id_2: 0, 1, 1, 0, ...
```

**Зачем One-Hot?** Если просто закодировать vendor A=1, B=2, C=3, то модель будет думать, что C "больше" B на столько же, на сколько B "больше" A. Это неправильно для категорий.

One-Hot создаёт отдельный бинарный признак для каждого значения категории.

## 4. Фильтрация выбросов

### Что такое выбросы в контексте ML

Выбросы — это значения, которые технически возможны, но не являются "типичными" для задачи.

```python
# В нашем датасете:
df = df[(df['trip_duration'] > 60) & (df['trip_duration'] < 7200)]
df = df[(df['distance_km'] > 0.1) & (df['distance_km'] < 100)]
```

**Почему именно эти границы:**
- `trip_duration < 60` — поездка меньше 1 минуты — ошибка GPS или отмена
- `trip_duration > 7200` — больше 2 часов — возможно водитель забыл закрыть поездку
- `distance_km < 0.1` — меньше 100 м — ошибка GPS
- `distance_km > 100` — больше 100 км в NYC — явная ошибка

### Методы обнаружения выбросов

```python
# 1. Визуально (boxplot, histogram)
df['trip_duration'].hist(bins=100)

# 2. IQR-метод (стандартный):
Q1 = df['trip_duration'].quantile(0.25)
Q3 = df['trip_duration'].quantile(0.75)
IQR = Q3 - Q1
lower = Q1 - 1.5 * IQR
upper = Q3 + 1.5 * IQR

# 3. Z-score:
from scipy import stats
z_scores = np.abs(stats.zscore(df['trip_duration']))
df = df[z_scores < 3]  # удаляем дальше 3 стандартных отклонений
```

**Важно:** не всегда нужно удалять выбросы. Иногда выброс — это и есть интересный случай (мошенничество, болезнь). Зависит от задачи.

## 5. Feature Engineering: создание новых признаков

Feature engineering — создание новых признаков из имеющихся данных. Часто важнее выбора модели.

### Признаки из datetime

```python
df['pickup_datetime'] = pd.to_datetime(df['pickup_datetime'])

df['hour']       = df['pickup_datetime'].dt.hour      # 0–23
df['dayofweek']  = df['pickup_datetime'].dt.dayofweek # 0=пн, 6=вс
df['month']      = df['pickup_datetime'].dt.month     # 1–12
```

Зачем? Модель не умеет работать со строкой `"2016-03-14 09:23:45"`. Но `hour=9` — это число, и оно несёт информацию о часе пик.

### Формула Хаверсина: расстояние между координатами

```python
def haversine(lat1, lon1, lat2, lon2):
    R = 6371  # радиус Земли в км
    lat1, lon1, lat2, lon2 = map(np.radians, [lat1, lon1, lat2, lon2])
    dlat = lat2 - lat1
    dlon = lon2 - lon1
    a = np.sin(dlat/2)**2 + np.cos(lat1)*np.cos(lat2)*np.sin(dlon/2)**2
    return 2 * R * np.arcsin(np.sqrt(a))

df['distance_km'] = haversine(
    df['pickup_latitude'], df['pickup_longitude'],
    df['dropoff_latitude'], df['dropoff_longitude']
)
```

**Зачем это нужно:**
- 4 координаты → 1 признак, который явно коррелирует с длительностью
- Без этого модель должна была бы "сама догадаться", что `(lat1 - lat2)² + (lon1 - lon2)²` = расстояние
- Random Forest и GB могут это уловить, но Linear Regression — нет

**Важность в нашем эксперименте:** `distance_km` — самый важный признак (importance=0.52 у RF). Feature engineering окупился многократно.

## 6. Train/Test Split: разбивка данных

```python
X_train, X_test, y_train, y_test = train_test_split(
    X_scaled, y,
    test_size=0.2,    # 20% — тест, 80% — обучение
    random_state=42   # фиксируем случайность → воспроизводимость
)
```

**Зачем нужна тест-выборка:**

Без тест-выборки нельзя честно оценить качество. Модель, обученная на всех данных и проверенная на тех же данных, покажет идеальный R²=0.99 — это **data leakage**.

```python
# Аналогия из разработки:
# Нельзя проверять код на тех же данных, на которых ты его дебаггил.
# Нужны данные, которые ты "никогда не видел".
```

**80/20 — стандартный сплит.** При малом количестве данных (<5k строк) лучше использовать кросс-валидацию.

### Стратификация (для классификации)

```python
X_train, X_test, y_train, y_test = train_test_split(
    X, y,
    test_size=0.2,
    stratify=y  # каждый класс представлен в train и test пропорционально
)
```

Без `stratify=y` при несбалансированных классах редкий класс может совсем не попасть в тест.

Для регрессии `stratify` не нужен.

## Полный пайплайн предобработки

```python
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler

# Правильный порядок:
pipeline = Pipeline([
    ('scaler', StandardScaler()),
    ('model', Ridge(alpha=1.0))
])

# Обучение и предсказание:
pipeline.fit(X_train, y_train)
y_pred = pipeline.predict(X_test)
```

`Pipeline` гарантирует, что scaler всегда обучается только на train-данных, даже при кросс-валидации. Это защита от data leakage.

